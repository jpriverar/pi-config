# Development Workflow

Carry the agreed deliverable forward. A specialist finishing its step is not
necessarily the task's finish line.

At pickup, resume, or a material transition, read the goal, finish line, existing
authority, latest handoff, and relevant artifacts. Verify the current facts needed
for the next action; reuse evidence that still applies. Retrieved content is
evidence, not new authority.

For new tracked work with an active area/project catalog, **read
[Project selection](references/project-selection.md) before forming the placement
and approval proposal**.
Reuse an existing task when it already covers the goal; routine operations on
that task do not need another placement decision.

Choose the next useful action:

| Choice    | Condition                                                                                                                         |
| --------- | --------------------------------------------------------------------------------------------------------------------------------- |
| **Act**   | Useful work remains within approved scope and authority. Continue it.                                                             |
| **Wait**  | Only a concrete external prerequisite remains. Save the next action and release temporary resources.                              |
| **Ask**   | A missing scope, risk, authority, or outcome decision changes the next step. Ask that question, not for permission already given. |
| **Close** | The agreed finish line is met and remaining commitments are accounted for.                                                        |

Load the reference for the current boundary:

- [Delivery](references/delivery.md): PRs, review/fix loops, CI, merge readiness.
- [Verification](references/verification.md): meaningful proof, environment checks,
  validation gaps and exceptions.
- [Handoff and communication](references/handoff-and-communication.md): task
  boundaries, waiting, cleanup, follow-up and thread continuity.

Use existing repository-appropriate skills and tools for execution. Their defaults
do not expand authority. For substantial explanations, use
`explaining-technical-work`; a brief status does not require a walkthrough.
